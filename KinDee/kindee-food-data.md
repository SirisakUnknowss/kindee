# KinDee — กลยุทธ์คลังข้อมูลอาหาร

เอกสารเสริมจาก kindee-architecture.md ข้อ 9

บริบท: ขยายขอบเขตจาก "อาหารไทย" เป็น "อาหารทั่วโลก + สินค้าในร้านค้าและห้าง"

## 1. สิ่งที่เปลี่ยนไปเมื่อขยายขอบเขต

การเพิ่มสินค้าบรรจุภัณฑ์เข้ามาไม่ใช่แค่ "เพิ่มข้อมูลเยอะขึ้น" แต่เปลี่ยนสถาปัตยกรรมหลายจุด

| เดิม (อาหารไทยอย่างเดียว) | ใหม่ (ทั่วโลก + สินค้าในร้าน) |
|---|---|
| ~500 รายการ bundle ลงเครื่องได้หมด | หลายล้านรายการ ต้องพึ่ง API + cache |
| ค้นด้วยชื่ออย่างเดียว | บาร์โค้ดกลายเป็นวิธีหลัก ชื่อเป็นรอง |
| หน่วยตวงไทย (จาน ทัพพี) | ต้องรองรับหน่วยบรรจุภัณฑ์ควบคู่ไปด้วย |
| แหล่งข้อมูลเดียว | 4 แหล่ง คุณภาพไม่เท่ากัน ต้องมีกติกาผสาน |
| ออฟไลน์ = ใช้ได้เกือบเต็มที่ | ออฟไลน์ = ค้นได้เฉพาะที่เคยใช้ ต้องออกแบบคิวรอ |
| ไม่มีประเด็นลิขสิทธิ์ซับซ้อน | มีเงื่อนไขสัญญาอนุญาตที่ต้องปฏิบัติตามจริงจัง |

**ผลกระทบที่ใหญ่ที่สุด:** งานเฟส 0 เปลี่ยนจาก "นั่งกรอกข้อมูล 500 จาน" เป็น "สร้างท่อรับข้อมูลจากหลายแหล่งแล้วผสานให้เป็นคลังเดียว" ซึ่งเป็นงานวิศวกรรมมากกว่างานกรอกข้อมูล แต่ก็ยังต้องกรอกอาหารไทยเองอยู่ดีเพราะไม่มีใครทำไว้ให้

## 2. แหล่งข้อมูลทั้ง 4

### 2.1 Open Food Facts — เสาหลักของสินค้าบรรจุภัณฑ์

ฐานข้อมูลเปิดที่ผู้ใช้ทั่วโลกช่วยกันสร้าง มีสินค้ามากกว่า 4 ล้านรายการ (ข้อมูลปี 2025) พร้อมบาร์โค้ด ข้อมูลโภชนาการ ส่วนประกอบ และรูปฉลาก

**ข้อดี**
- ครอบคลุมสินค้าทั่วโลกกว้างที่สุดในบรรดาฐานข้อมูลเปิด
- ค้นด้วยบาร์โค้ดได้ตรง ๆ ผ่าน API ที่เปิดให้ใช้ฟรี
- มีรูปสินค้าและรูปฉลากให้ด้วย ซึ่งช่วยให้ผู้ใช้มั่นใจว่าสแกนถูกชิ้น
- ดาวน์โหลดข้อมูลทั้งชุดมาเก็บเองได้ ไม่ต้องพึ่ง API ตลอดเวลา

**ข้อจำกัดที่ต้องรู้**
- **สินค้าไทยมีไม่ครบ** โดยเฉพาะของจากร้านสะดวกซื้อและแบรนด์ท้องถิ่น นี่คือช่องว่างที่ต้องอุดด้วยผู้ใช้ของเราเอง
- คุณภาพข้อมูลไม่สม่ำเสมอ เพราะมาจากอาสาสมัคร บางรายการมีแค่ชื่อ ไม่มีค่าโภชนาการ
- ข้อมูลอาจเก่า สูตรสินค้าเปลี่ยนแล้วแต่ในฐานข้อมูลยังเป็นของเดิม

**สัญญาอนุญาต: ODbL (Open Database License)**
ใช้ได้ทุกวัตถุประสงค์รวมถึงเชิงพาณิชย์ โดยมีเงื่อนไขสองข้อ คือ **ต้องให้เครดิต** และ **share-alike** — ถ้าเราเผยแพร่ฐานข้อมูลที่ดัดแปลงจากของเขา ต้องเผยแพร่ภายใต้สัญญาเดียวกัน

> **ข้อควรระวัง:** เงื่อนไข share-alike ของ ODbL มีรายละเอียดที่ตีความได้หลายแบบ โดยเฉพาะเส้นแบ่งระหว่าง "ใช้ฐานข้อมูลในแอป" กับ "เผยแพร่ฐานข้อมูลที่ดัดแปลง" ผมไม่ใช่ทนายและนี่ไม่ใช่คำแนะนำทางกฎหมาย ถ้าตั้งใจจะทำเชิงพาณิชย์จริงจัง ควรให้ผู้เชี่ยวชาญด้านกฎหมายดูก่อน — และควรถามตั้งแต่ตอนนี้ ไม่ใช่ตอนแอปโตแล้ว

### 2.2 USDA FoodData Central — วัตถุดิบและสินค้าอเมริกัน

ฐานข้อมูลของกระทรวงเกษตรสหรัฐฯ มีทั้งวัตถุดิบพื้นฐาน (Foundation, SR Legacy) และสินค้ามีแบรนด์ (Branded Foods)

**ข้อดี:** ข้อมูลวัตถุดิบพื้นฐานแม่นและครบถ้วนที่สุดในโลก เหมาะกับการใช้เป็นฐานคำนวณเมื่อต้องประกอบจานเอง และเป็นสาธารณสมบัติ (public domain) จึงไม่มีข้อผูกมัดเรื่องสัญญาอนุญาต

**ข้อจำกัด:** สินค้ามีแบรนด์เอียงไปทางตลาดอเมริกาเกือบทั้งหมด ใช้กับผู้ใช้ไทยได้น้อย

**บทบาทในระบบเรา:** ใช้เป็นแหล่งอ้างอิงสำหรับวัตถุดิบ ไม่ใช่แหล่งหลักของสินค้าในร้าน

### 2.3 Thai Food Composition Database (INMU มหิดล) — อาหารไทยปรุงสำเร็จ

ยังคงเป็นแหล่งที่ดีที่สุดสำหรับอาหารไทย ทำตามมาตรฐาน FAO/INFOODS เวอร์ชัน 3 ออกเมื่อสิงหาคม 2025

**เงื่อนไข:** ใช้ฟรีสำหรับวัตถุประสงค์ที่ไม่ใช่เชิงพาณิชย์ โดยต้องให้เครดิตสถาบันโภชนาการ ม.มหิดล

**สิ่งที่ต้องทำ:** ถ้าจะหารายได้จากแอป ต้องติดต่อขออนุญาตใช้เชิงพาณิชย์โดยตรง เรื่องนี้ยังคงเป็นความเสี่ยงอันดับต้น ๆ และควรเคลียร์ก่อนเริ่มงานจริง

**บทบาท:** ใช้เป็นฐานสำหรับวัตถุดิบและอาหารไทยพื้นฐาน แล้วเราประกอบเป็น "จาน" เอง เพราะฐานข้อมูลนี้เน้นวัตถุดิบมากกว่าจานสำเร็จตามร้าน

### 2.4 ผู้ใช้ช่วยกันเพิ่ม — ตัวอุดช่องว่างที่สำคัญที่สุด

สินค้าไทยจากร้านสะดวกซื้อ ห้าง และแบรนด์ท้องถิ่น จะหาไม่เจอในฐานข้อมูลไหนเลย ทางเดียวคือให้ผู้ใช้ช่วยกันเพิ่ม

**วิธีทำให้คนยอมช่วย**
- ต้องเจอหน้า "ไม่พบสินค้านี้" ตอนที่เขาถือของอยู่ในมือแล้ว — จังหวะนี้คือจังหวะเดียวที่คนยอมกรอก
- **ถ่ายรูปฉลากแล้วให้ระบบอ่านตัวเลขให้** ลดงานจากกรอก 6 ช่องเหลือกด 2 ครั้ง นี่คือกลไกที่ชี้ขาดว่าจะได้ข้อมูลหรือไม่
- ให้เลือกได้ว่าจะเก็บไว้ใช้เองหรือแชร์ให้คนอื่น อย่าแชร์อัตโนมัติ
- แสดงจำนวนที่เคยช่วยเพิ่มในหน้าโปรไฟล์ แค่นี้พอ ไม่ต้องทำระบบแต้ม

**ปัญหาที่ต้องรับมือ:** ข้อมูลผิด ข้อมูลซ้ำ และการก่อกวน ช่วงแรกที่ผู้ใช้ยังน้อยให้ตรวจเองทั้งหมด พอโตขึ้นค่อยทำระบบให้ผู้ใช้ยืนยันกันเอง (เช่น ต้องมีคนยืนยันตรงกัน 2 คนถึงเลื่อนระดับความน่าเชื่อถือ)

## 3. ลำดับความน่าเชื่อถือเมื่อข้อมูลชนกัน

เมื่อบาร์โค้ดเดียวกันมีข้อมูลจากหลายแหล่ง ให้เลือกตามลำดับนี้

1. **ข้อมูลที่ทีมตรวจสอบเองแล้ว** — สูงสุดเสมอ
2. **ข้อมูลที่ผู้ใช้หลายคนยืนยันตรงกัน** — น่าเชื่อกว่าฐานข้อมูลเปิดที่ไม่มีใครแตะมานาน
3. **Open Food Facts / USDA** ที่มีค่าโภชนาการครบ
4. **ข้อมูลจากผู้ใช้คนเดียว ยังไม่มีใครยืนยัน**
5. **ข้อมูลที่มีค่าโภชนาการไม่ครบ** — แสดงได้แต่ต้องเตือนว่าไม่ครบ

ทุกรายการต้องเก็บ `source` และ `verified_at` ไว้ และ UI ต้องแสดงระดับความน่าเชื่อถือให้ผู้ใช้เห็น — ความโปร่งใสตรงนี้สำคัญกว่าการแกล้งทำเป็นว่าข้อมูลทุกอันแม่นเท่ากัน

## 4. Schema ที่ต้องเพิ่มจากเวอร์ชันเดิม

```sql
foods (
  -- คอลัมน์เดิมทั้งหมด ...

  -- เพิ่มสำหรับสินค้าบรรจุภัณฑ์
  barcode          text unique,      -- EAN-13 / UPC
  brand            text,
  is_packaged      boolean default false,
  package_size_g   numeric,          -- ขนาดบรรจุทั้งซอง
  serving_size_g   numeric,          -- หน่วยบริโภคตามฉลาก
  servings_per_pkg numeric,          -- ฉลากบอกว่าซองนี้กี่หน่วยบริโภค
  image_url        text,
  label_image_url  text,

  -- สำหรับจัดการหลายแหล่ง
  source           text,             -- 'off' | 'usda' | 'inmu' | 'curated' | 'user'
  source_id        text,             -- id ในระบบต้นทาง ใช้ sync กลับ
  source_updated   timestamptz,
  quality          text,             -- 'verified' | 'community' | 'unverified' | 'incomplete'
  confirm_count    int default 0,    -- จำนวนผู้ใช้ที่ยืนยันว่าถูก
  region           text,             -- 'TH' | 'US' | 'global'
  contributed_by   uuid              -- ถ้าผู้ใช้เป็นคนเพิ่ม
)

create index on foods (barcode);
create index on foods (region, is_packaged);
```

**จุดที่พลาดกันบ่อยที่สุด: `package_size_g` กับ `serving_size_g` ต้องแยกกัน**
ฉลากขนมซอง 75 กรัมอาจเขียนว่า "หน่วยบริโภค 37.5 ก. / 2 หน่วยบริโภคต่อซอง" แต่คนกินทั้งซอง ถ้าระบบเก็บแค่ค่าเดียวแล้วเลือกผิด แคลอรีจะคลาดเคลื่อนไปครึ่งหนึ่งทันที และผู้ใช้จะไม่รู้ตัวเลย นี่เป็นข้อผิดพลาดที่พบในแอปนับแคลหลายตัว

## 5. วิธีดึงข้อมูล — API สดหรือดาวน์โหลดมาเก็บเอง

**แนะนำให้ทำทั้งสองอย่างผสมกัน**

```
ตอนสแกนบาร์โค้ด:
  1. หาในเครื่องก่อน (Dexie cache)         ← เร็วที่สุด ใช้ได้ออฟไลน์
  2. ไม่เจอ → หาใน DB ของเรา (Supabase)    ← เร็ว ควบคุมได้
  3. ไม่เจอ → เรียก API ภายนอก             ← ช้าสุด แต่ครอบคลุมสุด
  4. เจอแล้ว → เก็บลง DB เราและ cache ในเครื่อง
  5. ไม่เจอเลย → เปิดหน้าให้ผู้ใช้เพิ่มเอง
```

**เหตุผลที่ต้องเก็บสำเนาไว้เอง ไม่พึ่ง API อย่างเดียว**
- API ภายนอกอาจช้าหรือล่ม ซึ่งจะทำให้แอปเราใช้ไม่ได้ตามไปด้วย
- ยิ่งผู้ใช้เยอะ ยิ่งยิง API ถี่ ซึ่งไม่สุภาพกับบริการที่เขาให้ใช้ฟรี
- เราควบคุมคุณภาพและแก้ข้อมูลผิดเองไม่ได้ถ้าไม่มีสำเนา

**วิธีทำ:** ดาวน์โหลดชุดข้อมูลทั้งก้อนมาตั้งต้นครั้งแรก แล้วตั้งงานอัปเดตรายสัปดาห์ ส่วน API สดใช้เฉพาะกรณีสแกนแล้วไม่เจอในสำเนาของเรา

**คัดกรองก่อนนำเข้า:** ไม่ต้องเอามาทั้ง 4 ล้านรายการ กรองเอาเฉพาะที่มีค่าพลังงานครบและอยู่ในภูมิภาคที่เกี่ยวข้อง (ไทยและอาเซียนก่อน แล้วค่อยขยาย) จะเหลือขนาดที่จัดการไหวและค้นหาเร็วกว่ามาก

## 6. ผลกระทบต่อการทำงานออฟไลน์

เดิมตั้งใจ bundle คลังอาหารทั้งหมดลงเครื่อง ตอนนี้ทำไม่ได้แล้ว ต้องเปลี่ยนเป็น

```
bundle มากับแอป:     อาหารไทยยอดนิยม ~500 รายการ (ยังคงเดิม)
cache ในเครื่อง:      ทุกอย่างที่ผู้ใช้คนนี้เคยกินหรือเคยสแกน
คิวรอ:               บาร์โค้ดที่สแกนตอนออฟไลน์ รอค้นเมื่อกลับมาออนไลน์
```

**สถานการณ์จริงที่ต้องรองรับ:** คนอยู่ในห้างซึ่งสัญญาณมักไม่ดี สแกนของ 5 ชิ้นรวด ระบบต้องเก็บเลขบาร์โค้ดทั้ง 5 ไว้ก่อน แล้วค้นให้ทีเดียวเมื่อกลับมาออนไลน์ พร้อมแจ้งผลว่าเจอกี่ชิ้น ไม่เจอกี่ชิ้น — ห้ามทิ้งข้อมูลที่สแกนไปแล้วเด็ดขาด

## 7. แผนเฟส 0 ที่ปรับใหม่

| ขั้น | งาน | เวลา |
|---|---|---|
| 0.1 | เคลียร์เรื่องสัญญาอนุญาต — ติดต่อ ม.มหิดล และตรวจเงื่อนไข ODbL | 1–2 สัปดาห์ (ทำคู่ขนานกับงานอื่นได้) |
| 0.2 | สร้างท่อนำเข้าข้อมูล + คัดกรองเฉพาะภูมิภาคที่ต้องการ | 1–2 สัปดาห์ |
| 0.3 | กรอกอาหารไทยปรุงสำเร็จ 300–500 จานพร้อมหน่วยตวงไทย (งานมือ ไม่มีทางลัด) | 2–3 สัปดาห์ |
| 0.4 | ทำระบบผสานข้อมูลและจัดระดับความน่าเชื่อถือ | 1 สัปดาห์ |
| 0.5 | ทดสอบสแกนของจริงในร้านสะดวกซื้อและห้าง วัดว่าเจอกี่เปอร์เซ็นต์ | 3–5 วัน |

**ขั้น 0.5 สำคัญกว่าที่คิด** — ก่อนลงแรงสร้างแอปทั้งตัว ให้เดินเข้าร้านสะดวกซื้อแล้วสแกนของสัก 50 ชิ้นดูก่อนว่าฐานข้อมูลเปิดครอบคลุมสินค้าไทยกี่เปอร์เซ็นต์ ตัวเลขนี้จะบอกได้ทันทีว่าต้องพึ่งผู้ใช้ช่วยเพิ่มมากแค่ไหน และควรออกแบบ flow "เพิ่มสินค้าเอง" ให้ดีขนาดไหน

ถ้าผลออกมาต่ำกว่า 30% แปลว่า flow เพิ่มสินค้าเองไม่ใช่ฟีเจอร์เสริม แต่เป็นฟีเจอร์หลักที่ต้องขัดให้ดีพอ ๆ กับการสแกน

## 8. ความเสี่ยงที่เพิ่มขึ้นจากการขยายขอบเขต

| ความเสี่ยง | ระดับ | รับมือ |
|---|---|---|
| เงื่อนไข share-alike ของ ODbL กระทบโมเดลธุรกิจ | สูง | ปรึกษาผู้เชี่ยวชาญกฎหมายก่อนทำเชิงพาณิชย์ |
| ลิขสิทธิ์ Thai FCD เชิงพาณิชย์ | สูง | ติดต่อ ม.มหิดล ตั้งแต่ตอนนี้ |
| สินค้าไทยในฐานข้อมูลเปิดมีน้อยเกินไป | สูง | วัดจริงในขั้น 0.5 แล้วทุ่มกับ flow เพิ่มสินค้าเอง |
| ข้อมูลจากผู้ใช้ผิดหรือถูกก่อกวน | กลาง | ระบบยืนยัน + ตรวจเองช่วงแรก + ปุ่มแจ้งข้อมูลผิด |
| ข้อมูลเก่า สูตรสินค้าเปลี่ยนแล้ว | กลาง | แสดงวันที่อัปเดตล่าสุด + อัปเดตรายสัปดาห์ |
| ผู้ใช้เลือกหน่วยผิดระหว่างซองกับหน่วยบริโภค | กลาง | ตั้งค่าเริ่มต้นเป็นทั้งซอง + แสดงให้ชัดว่ากำลังนับแบบไหน |
