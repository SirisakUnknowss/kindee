# KinDee — โครงสร้างแอป

แอปนับแคลอรีที่เข้าใจอาหารไทย
เวอร์ชันเอกสาร: 0.1 — 31 กรกฎาคม 2026

---

## 1. หลักการออกแบบ

สี่ข้อนี้เป็นตัวตัดสินใจทุกอย่างที่ตามมา ถ้าลังเลตรงไหนให้ย้อนกลับมาอ่าน

**1. อาหารไทยเป็นจาน ไม่ใช่วัตถุดิบ**
คนไทยไม่ได้กิน "ข้าวสวย 150 กรัม + ไก่ผัดใบกะเพรา 120 กรัม + ไข่ดาว 1 ฟอง" — เขากิน "กะเพราไก่ไข่ดาว" หนึ่งจาน ระบบต้องบันทึกระดับจานเป็นค่าเริ่มต้น แล้วค่อยให้แตกส่วนประกอบทีหลังถ้าอยาก

**2. หน่วยตวงต้องเป็นหน่วยที่คนไทยใช้จริง**
ทัพพี จาน ถ้วย ชาม ไม้ ลูก แก้ว — ไม่ใช่กรัม ไม่มีใครชั่งอาหารก่อนกิน ถ้าบังคับให้กรอกกรัม แอปตายตั้งแต่สัปดาห์แรก

**3. ลด friction ให้เหลือน้อยที่สุด**
เป้าหมายคือบันทึกหนึ่งมื้อจบใน 3 วินาที ทุกฟีเจอร์ที่เพิ่มขั้นตอนต้องพิสูจน์ตัวเองว่าคุ้ม ปุ่ม "กินซ้ำเมื่อวาน" มีค่ามากกว่าฟีเจอร์หรู ๆ สิบอย่าง

**4. แอปต้องไม่ผลักคนไปหาพฤติกรรมการกินที่ไม่ดี**
ไม่มีข้อความตำหนิเมื่อกินเกิน ไม่มีการตั้งเป้าแคลอรีต่ำกว่าเกณฑ์ปลอดภัย ไม่มี streak ที่ทำให้รู้สึกผิดตอนพลาด นี่ไม่ใช่แค่เรื่องจริยธรรม — แอปที่ทำให้คนรู้สึกแย่คือแอปที่คนลบทิ้ง

## 2. Stack

## 4. Data model

```sql
-- โปรไฟล์ + เป้าหมาย
profiles (
  id            uuid pk references auth.users,
  sex           text,              -- 'male' | 'female'
  birth_date    date,
  height_cm     numeric,
  activity      text,              -- sedentary | light | moderate | active
  goal          text,              -- lose | maintain | gain
  target_kcal   int,               -- คำนวณแล้ว แต่แก้เองได้
  target_source text,              -- 'auto' | 'manual'
  created_at    timestamptz
)

-- น้ำหนักเก็บแยก เพราะเปลี่ยนตลอด
weight_logs (id, user_id, weight_kg, logged_on date, unique(user_id, logged_on))

-- คลังอาหาร
foods (
  id           uuid pk,
  name_th      text not null,
  name_en      text,
  aliases      text[],            -- 'กะเพราไก่', 'ผัดกะเพราไก่', 'กระเพราไก่'
  category     text,              -- จานเดียว | กับข้าว | ของหวาน | เครื่องดื่ม | ผลไม้
  is_dish      boolean,           -- true = จานสำเร็จ, false = วัตถุดิบ
  kcal_100g    numeric not null,
  protein_100g numeric,
  carb_100g    numeric,
  fat_100g     numeric,
  source       text,              -- 'inmu' | 'curated' | 'user'
  verified     boolean default false,
  search_text  text               -- normalize แล้ว ใช้ทำ index
)

-- หน่วยตวงแบบไทย — หัวใจของ UX
food_portions (
  id          uuid pk,
  food_id     uuid references foods,
  label_th    text not null,      -- '1 จาน', '1 ทัพพี', '1 ไม้', '1 ถ้วย'
  grams       numeric not null,
  is_default  boolean
)

-- แตกจานเป็นส่วนประกอบ (optional, ใช้ตอนผู้ใช้อยากปรับ)
food_components (dish_id uuid, food_id uuid, grams numeric, primary key(dish_id, food_id))

-- รายการที่กิน
entries (
  id           uuid pk,
  user_id      uuid,
  food_id      uuid references foods,
  portion_id   uuid references food_portions,
  qty          numeric default 1,
  grams        numeric not null,     -- คำนวณแล้ว เก็บไว้เลย
  meal         text,                 -- breakfast | lunch | dinner | snack
  eaten_at     timestamptz,
  eaten_on     date,                 -- denormalize ไว้ query ง่าย
  kcal         numeric not null,     -- snapshot
  protein      numeric, carb numeric, fat numeric,
  entry_source text,                 -- search | recent | photo | manual
  photo_path   text,
  client_id    text unique           -- id ที่สร้างจากเครื่อง ใช้กันบันทึกซ้ำตอน sync
)

-- สรุปรายวัน — อัปเดตด้วย trigger เพื่อให้กราฟเร็ว
daily_summaries (
  user_id uuid, date date,
  kcal numeric, protein numeric, carb numeric, fat numeric,
  entry_count int, target_kcal int,
  primary key (user_id, date)
)

streaks (user_id uuid pk, current int, longest int, last_logged_on date, freezes_left int default 2)

-- ติดตามต้นทุน AI
photo_jobs (id, user_id, image_hash, status, candidates jsonb, cost_cents, created_at)
```

**จุดที่ต้องไม่พลาด: `entries` เก็บ `kcal` เป็น snapshot**
ถ้าวันหลังแก้ข้อมูลโภชนาการของ "ผัดกะเพรา" ประวัติย้อนหลังของผู้ใช้ต้องไม่เปลี่ยนตาม ไม่งั้นกราฟเมื่อเดือนที่แล้วจะขยับเองโดยไม่มีเหตุผล ผู้ใช้จะเลิกเชื่อถือข้อมูลทันที

**RLS** เปิดทุกตารางที่มี `user_id` — `foods` กับ `food_portions` อ่านได้ทุกคน เขียนได้เฉพาะ service role

## 5. หน้าจอ

| หน้า | มีอะไร |
|---|---|
| **Onboarding** | เพศ / วันเกิด / ส่วนสูง / น้ำหนัก / ระดับกิจกรรม / เป้าหมาย → แสดงเป้าแคลพร้อมคำอธิบายว่าคำนวณมายังไง |
| **วันนี้** | วงแหวนความคืบหน้า, เหลืออีกกี่แคล, รายการแยกตามมื้อ, ปุ่มเพิ่มลอยอยู่มุมล่าง |
| **เพิ่มอาหาร** | แท็บ: ล่าสุด / ค้นหา / ถ่ายรูป — "ล่าสุด" ต้องเป็นแท็บแรกเพราะคนกินซ้ำเยอะ |

## 6. ตรรกะสำคัญ

### 6.1 คำนวณเป้าแคลอรี

ใช้สูตร Mifflin-St Jeor ซึ่งเป็นมาตรฐานที่แม่นกว่า Harris-Benedict สำหรับคนทั่วไป

```
BMR = 10 × น้ำหนัก(kg) + 6.25 × ส่วนสูง(cm) − 5 × อายุ + s
      s = +5 (ชาย), −161 (หญิง)

TDEE = BMR × ตัวคูณกิจกรรม
      นั่งทำงานเป็นหลัก 1.2 / เบา 1.375 / ปานกลาง 1.55 / หนัก 1.725

เป้า = TDEE − 15%   (ลดน้ำหนัก)
     = TDEE          (คงน้ำหนัก)
     = TDEE + 10%    (เพิ่มน้ำหนัก)
```

**ตัวกันด้านล่าง (สำคัญมาก)** — ไม่ว่าคำนวณออกมาได้เท่าไร เป้าต้องไม่ต่ำกว่า BMR และไม่ต่ำกว่า 1,200 kcal สำหรับผู้หญิง / 1,500 kcal สำหรับผู้ชาย ถ้าผู้ใช้พยายามตั้งต่ำกว่านั้นเอง ให้แสดงคำเตือนและแนะนำให้ปรึกษาแพทย์หรือนักกำหนดอาหาร ไม่ใช่ปล่อยผ่านเงียบ ๆ

เก็บ `target_source` ไว้ด้วย เพราะถ้าผู้ใช้ตั้งเอง เราไม่ควรไปเขียนทับตอนเขาอัปเดตน้ำหนัก

### 6.2 ค้นหาภาษาไทย

ปัญหาจริงที่ต้องแก้ก่อนเขียนโค้ด:

- คนพิมพ์ผิดวรรณยุกต์และสระตลอด — "กระเพรา" vs "กะเพรา" ต้อง match กัน
- ไม่มีเว้นวรรค — "ข้าวมันไก่ต้ม" ต้องเจอ
- พิมพ์ไม่ครบ — "กะเพ" ต้องขึ้นแล้ว

วิธี: สร้างคอลัมน์ `search_text` ที่ผ่านการ normalize (ตัดวรรณยุกต์ ตัดเว้นวรรค แปลงสระที่สับสนกันบ่อย) แล้วใช้ Postgres `pg_trgm` ทำ fuzzy match ส่วน `aliases[]` เก็บคำที่คนเรียกกันจริงแบบ manual

ผลลัพธ์เรียงตาม: ตรงเป๊ะ → ขึ้นต้นตรง → เคยกิน → ยอดนิยม → fuzzy

### 6.3 ถ่ายรูปแล้วให้ AI ทาย

ออกแบบให้ปลอดภัยทั้งด้านต้นทุนและด้านความน่าเชื่อถือ

```
client: ถ่ายรูป → ย่อเหลือ ≤1024px, JPEG q75 → hash
  ↓
server route: เช็ค rate limit → เช็ค cache ด้วย hash → เรียก vision API
  ↓
prompt: บังคับให้ตอบเป็นชื่อจานจาก "รายการที่เรามีในคลัง" เท่านั้น + ความมั่นใจ + ปริมาณที่เดา
  ↓
คืน candidate 3 อันดับ → ผู้ใช้เลือกและยืนยันเสมอ
```

กติกาที่ห้ามละเมิด:

- **ห้ามบันทึกอัตโนมัติ** ผู้ใช้ต้องกดยืนยันทุกครั้ง การเดาผิดแล้วบันทึกเองคือวิธีทำลายความเชื่อถือที่เร็วที่สุด
- **จำกัดโควตา** เช่น 5 ครั้ง/วันสำหรับผู้ใช้ทั่วไป ไม่งั้นค่า API บานปลายตามจำนวนผู้ใช้
- **ให้ AI เลือกจากคลังที่เรามี** ไม่ใช่ตอบอิสระ ไม่งั้นจะได้ชื่อจานที่ map กลับเข้าฐานข้อมูลไม่ได้
- แสดงความมั่นใจให้เห็น ถ้าต่ำให้บอกตรง ๆ ว่า "ไม่ค่อยแน่ใจ ลองค้นหาแทนไหม"

### 6.4 Streak แบบให้อภัย

streak ที่ขาดแล้วรีเซ็ตเป็นศูนย์คือกลไกที่ทำให้คนเลิกใช้แอป พลาดวันเดียวแล้วรู้สึกว่าพังหมดแล้ว เลยเลิกไปเลย

ทำแบบนี้แทน: ให้ freeze 2 ครั้งต่อเดือนแบบอัตโนมัติ ขาดหนึ่งวันไม่รีเซ็ต และเน้นแสดง "บันทึกไป 18 วันจาก 30 วัน" มากกว่าตัวเลข streak ติดต่อกัน

## 7. Offline-first

PWA ที่ใช้ไม่ได้ตอนสัญญาณไม่ดีคือ PWA ที่ไร้ประโยชน์ — คนบันทึกอาหารตอนอยู่ในร้าน ซึ่งเป็นที่ที่เน็ตแย่ที่สุด

```
Dexie เก็บ:
  foods_cache      คลังอาหารยอดนิยม ~500 รายการ (bundle มากับแอปเลย)
  entries_local    รายการที่บันทึก มี client_id เป็น key
  outbox           คิวรอ sync

เมื่อออนไลน์: ส่ง outbox → server upsert ด้วย client_id (idempotent) → เคลียร์คิว
```

`client_id` เป็น unique key ทำให้กดซ้ำหรือ sync ซ้ำก็ไม่เกิดข้อมูลซ้ำ entries เป็นข้อมูลแบบเพิ่มอย่างเดียวเป็นส่วนใหญ่ conflict จึงน้อยมาก ใช้ last-write-wins ก็พอ

ข้อควรรู้เรื่อง iOS: Safari มีข้อจำกัดเรื่อง storage ที่อาจถูกล้างถ้าไม่ได้เปิดแอปนาน และการติดตั้ง PWA ต้องทำผ่านเมนู Share เอง — ต้องมีหน้าสอนวิธีติดตั้ง ไม่งั้นคนส่วนใหญ่จะไม่รู้

## 8. แผนการทำ

| เฟส | ทำอะไร | เวลาโดยประมาณ |
|---|---|---|
| **0. คลังอาหาร** | รวบรวมและทำความสะอาดข้อมูล 300–500 จานที่คนไทยกินบ่อยที่สุด + กำหนดหน่วยตวงและน้ำหนักต่อหน่วย | 2–3 สัปดาห์ |

เคล็ดลับ: อาหารประมาณ 200 จานครอบคลุมสิ่งที่คนไทยกินจริงราว 80% เริ่มจากเมนูตามศูนย์อาหารและร้านข้างทาง ไม่ต้องเริ่มจากอาหารหรู

## 9. แหล่งข้อมูลโภชนาการ

**Thai Food Composition Database (Thai FCD)** โดยสถาบันโภชนาการ มหาวิทยาลัยมหิดล — เวอร์ชัน 3 (สิงหาคม 2025) เป็นฐานข้อมูลที่ทำตามมาตรฐาน FAO/INFOODS และเป็นแหล่งที่น่าเชื่อถือที่สุดสำหรับอาหารไทย

**เงื่อนไขการใช้งาน:** ใช้ฟรีสำหรับวัตถุประสงค์ที่ไม่ใช่เชิงพาณิชย์ โดยต้องให้เครดิตสถาบันโภชนาการ ม.มหิดล อย่างเหมาะสม

**สิ่งที่ต้องทำก่อนไปไกลกว่านี้:** ถ้าวางแผนจะหารายได้จากแอปในอนาคต ต้องติดต่อสถาบันเพื่อขออนุญาตใช้เชิงพาณิชย์ให้ชัดเจนก่อน อย่ารอจนสร้างแอปเสร็จแล้วค่อยถาม — เรื่องนี้ควรเคลียร์ตั้งแต่ก่อนเริ่มเฟส 0

ข้อจำกัดอีกอย่าง: ฐานข้อมูลนี้เน้นวัตถุดิบและอาหารพื้นฐานมากกว่าจานสำเร็จตามร้าน ดังนั้นสำหรับ "กะเพราไก่ไข่ดาว" อาจต้องประกอบเองจากส่วนประกอบ แล้วให้ผู้ใช้ช่วยยืนยันความสมเหตุสมผลอีกที

## 10. ความเสี่ยงที่ต้องจับตา

| ความเสี่ยง | ระดับ | รับมือ |
|---|---|---|
| ลิขสิทธิ์ฐานข้อมูลตอนทำเชิงพาณิชย์ | สูง | ติดต่อ ม.มหิดล ก่อนเริ่มเฟส 0 |
| ค่า vision API บานปลาย | สูง | โควตารายวัน + cache ด้วย hash + ย่อรูปก่อนส่ง |
| คนเลิกใช้ภายในสัปดาห์แรก | สูง | ลด friction, ปุ่มกินซ้ำ, streak แบบให้อภัย |
| ข้อมูลจานสำเร็จไม่แม่น | กลาง | บอกช่วงค่าแทนตัวเลขเป๊ะ + ให้ผู้ใช้แจ้งแก้ไข |
| ผู้ใช้ตั้งเป้าต่ำเกินไป | กลาง | ตัวกันด้านล่าง + ข้อความเตือน |
| iOS ล้าง storage | ต่ำ | sync ขึ้น server ทันทีที่ออนไลน์ |

## 11. สิ่งที่ยังไม่ตัดสินใจ

- ชื่อโดเมนและชื่อใน App Store (ยังไม่ได้เช็คว่าซ้ำไหม)
- โมเดลรายได้ — ฟรีทั้งหมด / จำกัดโควตารูป / subscription
- จะมีระบบให้ผู้ใช้ช่วยกันเพิ่มอาหารไหม (ได้ข้อมูลเยอะแต่คุณภาพคุมยาก)
- แสดง macro (โปรตีน/คาร์บ/ไขมัน) ตั้งแต่แรกหรือซ่อนไว้ก่อน — เพิ่มความซับซ้อนแลกกับความมีประโยชน์
