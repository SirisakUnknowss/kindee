# ขั้นตอนรับมือเหตุละเมิดข้อมูลส่วนบุคคล (PDPA)

เจ้าของเอกสาร: ผู้ควบคุมข้อมูลส่วนบุคคลของ KinDee  
ช่องทางแจ้งเหตุภายใน: กำหนดก่อน production  
ปรับปรุงล่าสุด: 15 กันยายน 2026

> เอกสารนี้เป็น runbook ปฏิบัติการ ไม่ใช่คำปรึกษากฎหมาย เมื่อเกิดเหตุให้ผู้รับผิดชอบ PDPA/ที่ปรึกษากฎหมายตรวจเกณฑ์การแจ้งตามข้อเท็จจริง

## 1. รับแจ้งและเริ่มนับเวลา

1. ผู้พบเหตุแจ้ง incident lead ทันที ห้ามลบ log หรือหลักฐาน
2. incident lead บันทึกเวลา `T0` ซึ่งองค์กรทราบเหตุ ผู้รายงาน ระบบ/บัญชีที่เกี่ยวข้อง และเปิด incident ID
3. จัดชั้นความลับของห้องสื่อสารและจำกัดผู้เข้าถึงแบบ need-to-know
4. เริ่ม timeline 72 ชั่วโมงตั้งแต่ T0 โดยไม่รอให้การสืบสวนเสร็จ

## 2. ควบคุมเหตุภายใน 0–4 ชั่วโมง

- ถอนหรือหมุน secret/API key ที่สงสัย ปิด session และบัญชีที่ถูกยึด
- จำกัด endpoint, bucket, table หรือ deployment ที่เป็นต้นเหตุ โดยเก็บ snapshot/log ที่จำเป็นก่อน
- ติดต่อ Supabase, Cloudflare หรือ Google ตามช่องทาง security/DPA หากระบบของผู้ประมวลผลเกี่ยวข้อง
- ห้ามนำข้อมูลจริงไปวางใน ticket หรือ chat ที่ไม่มีการควบคุมสิทธิ

## 3. ประเมินผลกระทบภายใน 4–24 ชั่วโมง

บันทึกอย่างน้อย:

- ประเภทเหตุ: ความลับ ความถูกต้อง หรือความพร้อมใช้
- ประเภทข้อมูล: อีเมล วันเกิด เพศ ส่วนสูง น้ำหนัก เป้าหมาย รายการอาหาร รูปภาพ token หรือ log
- จำนวนและกลุ่มเจ้าของข้อมูล รวมผู้เยาว์หรือกลุ่มเปราะบางถ้ามี
- ข้อมูลถูกอ่าน ดาวน์โหลด แก้ไข หรือลบจริงหรือเป็นเพียงความเป็นไปได้
- ผู้รับที่ไม่พึงประสงค์ ระยะเวลาที่เปิดเผย การเข้ารหัส/การทำ pseudonym และความสามารถในการนำข้อมูลไประบุตัว
- ผลที่อาจเกิด เช่น สวมรอย เลือกปฏิบัติ อับอาย ความเสียหายต่อสุขภาพหรือการเงิน
- มาตรการที่ทำแล้วและความเสี่ยงคงเหลือ

ให้จัดผลเป็น (ก) ไม่น่ามีความเสี่ยง (ข) มีความเสี่ยง หรือ (ค) มีความเสี่ยงสูง พร้อมเหตุผลและผู้อนุมัติ ห้ามใช้จำนวน record เพียงอย่างเดียวตัดสิน

## 4. การแจ้งภายนอก

- หากเหตุมีความเสี่ยงต่อสิทธิและเสรีภาพ แจ้งสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคลโดยไม่ชักช้าภายใน 72 ชั่วโมงนับแต่ทราบเหตุ เท่าที่ทำได้
- ถ้าแจ้งเกิน 72 ชั่วโมง ให้แนบเหตุผลความล่าช้า
- ถ้ามีความเสี่ยงสูง ให้แจ้งเจ้าของข้อมูลโดยไม่ชักช้า ด้วยภาษาที่ชัดเจน ผ่านช่องทางที่มีโอกาสถึงผู้รับ
- หนังสือแจ้งควรมีลักษณะเหตุ ประเภท/จำนวนข้อมูลและบุคคล ผลกระทบที่อาจเกิด มาตรการแก้ไข วิธีที่ผู้ใช้ป้องกันตนเอง และช่องทางติดต่อ
- หากยังทราบไม่ครบ ให้แจ้งข้อมูลที่มีและส่งเพิ่มเติมเป็นระยะตามที่กฎหมายอนุญาต

## 5. ฟื้นฟูและหลังเหตุ

1. ทดสอบการแก้ไขใน staging แล้วจึงคืนระบบ พร้อม monitoring เฉพาะเหตุ
2. ตอบคำถามและคำขอใช้สิทธิของผู้ได้รับผลกระทบผ่าน `VITE_PRIVACY_EMAIL`
3. เก็บทะเบียนเหตุ การประเมิน เหตุผลที่แจ้ง/ไม่แจ้ง การสื่อสาร และหลักฐานการแก้ไขอย่างจำกัดสิทธิ
4. ทำ post-incident review ภายใน 10 วันทำการ กำหนด owner และวันปิด remediation
5. ทบทวน Privacy Notice, retention, RLS, secret rotation และสัญญาผู้ประมวลผลเมื่อเหตุชี้ว่าข้อมูลเปลี่ยนไป

## แบบฟอร์ม incident ขั้นต่ำ

```text
Incident ID:
T0 / ผู้พบเหตุ:
Incident lead / ผู้ตัดสินใจด้านกฎหมาย:
ระบบและช่วงเวลาที่ได้รับผล:
ข้อมูลและจำนวนเจ้าของข้อมูล:
กลุ่มเปราะบาง:
หลักฐานการเข้าถึง/นำออก:
มาตรการควบคุม:
ระดับความเสี่ยงและเหตุผล:
กำหนดแจ้ง PDPC (T0 + 72h):
การแจ้งเจ้าของข้อมูล:
ผู้ประมวลผลที่ติดต่อ:
สถานะและงานแก้ไขถาวร:
```

แหล่งอ้างอิงหลัก: พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 โดยเฉพาะหน้าที่ด้านมาตรการความมั่นคงปลอดภัยและการแจ้งเหตุ และประกาศ/แนวทางล่าสุดของสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล
